# 004 — Internationalisation

## Context

The user writes in French, the academic report is in French, but the
application is meant to be usable by anyone. The backend returns the menu
content and the notification messages in a single language.

## Decision

- The default UI language is **English** for everybody. The browser language is
  deliberately **not** consulted: two visitors on the same page must see the
  same language until one of them opens the switcher.
- The chosen language is stored under the key `restaurant.locale` and applied
  on the next visit.
- Translations live in `src/i18n/locales/{en,fr}/<namespace>.json`. Each
  namespace covers one area of the UI (menu, orders, billing, ...). The files
  are merged in `src/i18n/index.js` and exposed through `$t`.
- **Both languages must define exactly the same keys, with the same
  `{placeholders}` and no empty string.** A unit test enforces this on every
  run. Adding a key means adding it twice.
- Plurals use the vue-i18n pipe syntax and are called with a third argument:
  `$t('queue.waiting', { count: n }, n)`.
- **Menu content and notification messages are not translated**: they come from
  the backend, which does not know the visitor's language. This is a known
  limitation, listed in the backend's maintenance backlog.

## Consequences

- A missing key falls back to English, never to a raw key, because the parity
  test fails the build before it can ship.
- The locale switcher is the only place where `applyLocale` is called; every
  other file reads `locale` from the `ui` store.
